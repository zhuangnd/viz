01

需求拆解与核心概念

把「查询指定站点的高铁动车路线图」拆成可执行的数据与展示两半：数据侧解决「哪些车次经过该站、各自停哪些站、什么时刻」，展示侧解决「在地图上把线路画出来、可筛选可联动」。

输入任意站点名称（如「厦门北站」），系统输出三份能力：① 车次清单——全部经该站的高铁（G）/ 动车（D）/ 城际（C）车次及其关系分类；② 线路画像——每个车次的经停序列、到发时刻、停站时长、区间时长、全程时长；③ 地图视图——车次线路沿地理走向绘制，站点按关系类型着色，支持点击联动与时段筛选。

始发 该站为车次首站

车次在该站开始载客，停靠序列中序号为 1（seq=1），页面以实心橙标站点、线头加粗表示。

判定：stop.seq === 1

终到 该站为车次末站

车次在该站终到折返，停靠序列中序号为末位（seq=N），页面以空心蓝标站点、线尾收束表示。

判定：stop.seq === N

途经 该站为中间经停站

车次在该站短暂停靠后继续前行，停靠序列中 1<seq<N，页面以灰点站点、细线过站表示。

判定：1 < stop.seq < N
  • 车站与车次数据字典（电报码 / 经纬度 / 车种）
  • 采集与校验脚本（低频节流、可断点续跑）
  • 关系型存储（车站 / 车次 / 停靠 / 线路）
  • 只读查询服务（REST / JSON）
  • 地图可视化页面（Web，桌面 + 移动端）
  • 定时更新任务（每日增量 + 调图全量）
02

数据源调研与选型

经调研，可用数据源分四类：12306 官方页面与接口、第三方数据聚合服务、开放地图与线路几何数据、公开新闻公告。下表逐一比对覆盖范围、时效、成本与合规风险，给出分级选型结论。

数据源 / 接口类型与获取方式覆盖与时效成本合规等级用途定级
kyfw.12306.cn/otn/czxx/init 车站车次查询 官方「车站车次」查询页与底层接口（POST 需会话 cookie），按车站返回全部车次及到站时刻、历时 全国全列，与售票系统同步免费 个人/内部演示可低频使用；公开发布与商业使用需书面授权 P0 主数据

方案 A · 自建轻量采集

会话初始化获取 cookie → 站点代码表 → 车站车次查询 → 逐车次经停补齐 → 校验入库。全流程可控、零成本。

适用：个人学习 / 内部演示 / 原型验证

方案 B · 第三方授权 API

购买商业数据服务（时刻、站站查询），按调用量计费，规避自建采集的合规与稳定性负担。

适用：公开发布 / 商业产品

方案 C · 混合

自建采集做主数据（低频节流），第三方 API 做交叉校验与兜底，公告做调图触发。

适用：长期运营 / 需保障数据质量

03

数据模型设计

核心是「车次—停靠」关系：一趟车次是一串按序排列的停靠记录，站点是这些记录的位置锚点。路线图即「从指定站点出发，沿每趟车次的停靠序列连成的折线集合」。

station 车站
  • station_id 主键
  • code 电报码（唯一，厦门北=XMS）
  • name 站名（厦门北站）
  • name_py 拼音首字母
  • city / province 行政区
  • lon / lat 经纬度
train 车次
  • train_no 车次号（G2372）
  • train_type 车种 G/D/C…
  • origin_id 始发站
  • dest_id 终到站
  • total_min 全程时长
  • calendar 开行规律（每日/周末/高峰线）
  • src / updated_at 来源与版本
stop 停靠
  • id 主键
  • train_no 所属车次
  • seq 站序（1=始发）
  • station_id 车站
  • arrive / depart 到时 / 发时
  • stop_min 停站时长
  • seg_min 与上一站区间时长
train 1 ——N stop　·　station 1 ——N stop
关键查询逻辑（指定站点 → 路线图）实现要点
① 定位站点输入站名 → 电报码归一（解决「厦门北 / 厦门北站」别名），取 station
② 找出车次stop 表按 station_id 关联出全部车次；按 seq 判定关系：seq=1 始发、seq=N 终到、其余途经
③ 展开线路对每个车次取完整停靠序列（seq 升序），拼接站点坐标与线路几何 → GeoJSON Polyline
④ 计算时长区间时长 = 到达时刻差（跨日自动 +24h 标记「次日」）；全程时长 = 末站到 - 首站发
⑤ 派生视图线路（route）= 同一走向多车次聚合线，按车次数分级（粗=多车次走廊）

存储选型：原型期 SQLite 单文件即可（万级停靠记录毫秒级查询）；规模化切 PostgreSQL + 空间索引（PostGIS）。

04

数据采集与更新策略

采集遵循「低频、节流、可追溯」三原则：只取开行计划与时刻表，不抓余票；单站全量车次一次拉取，全流程断点续跑；每条数据落库都带抓取时间与来源，便于审计与回滚。

STEP 01
会话初始化

访问 12306 车站查询页获取会话 cookie（JSESSIONID 等），UA 轮换

STEP 02
站点字典

解析 station_name_v10036.js，站名 ↔ 电报码归一，过滤高铁/动车/城际站

STEP 03
车站车次查询

逐目标站请求车站车次接口，得车次、到时/发时、到站历时

STEP 04
经停补齐

对每个车次拉完整经停序列（站序/时刻），第三方 API 抽样交叉核对

STEP 05
规则校验

时间单调、区间时长自洽、跨日标记、停站时长 >0，异常进对账队列

STEP 06
入库与版本

增量 upsert，写 data_version 快照，调图后全量重建

更新策略

触发时机范围方式

·

校验规则

规则说明
时刻单调递增同一车次后续站到时 >= 前站发时
区间时长自洽seg_min ≈ 到时差 - 停站时长，容差 ±2min
跨日标记次日到达标注「+1」，避免 24 点误解
多源交叉第三方 API 抽样比对，不一致告警
开行规律区分每日线 / 周末线 / 高峰线，避免漏线误判

节流与容错：请求间隔 ≥5s 加随机抖动、失败指数退避（上限 5 次）、断点续传、全量日志留痕；单站全量约 30–60 秒内完成，日均调用量控制在百次以内，不对 12306 造成任何实质负载。

本方案最大的不确定性不在技术，而在数据来源的合规与时效。下表按影响从高到低列出主要风险与处置预案。

风险影响处置预案
数据版权12306 使用条款明确未经书面许可不得复制、发布或商业使用其内容默认仅个人/内部低频采集与缓存；公开发布或商业化前切换第三方授权 API 或与国铁数据服务商洽谈授权
反爬封禁高频或异常请求触发限流、封禁请求间隔 ≥5s + 随机抖动、UA/cookie 池、指数退避、全量日志；不抓余票、不碰购票链路
数据时效车票售罄或预售期内方案调整的车次，官方页面不显示以开行计划口径为准，页面标注数据抓取时间；每日增量兜底修正
调图变更一年约 1–2 次大调图（如 2026-07-01），时刻表大面积变化公告监控触发全量重建，保留上一基线可回滚，重建后自动对账
同名 / 别名站点「冠豸山」与「冠豸山南」易混、站名别名多电报码为唯一主键，建立名称归一表，搜索走别名映射

合规红线：本方案默认形态定位为「个人学习 / 内部研究 / 原型演示」。若用于对外公开发布或商业产品，必须完成两步——① 数据获取切换到已授权渠道（第三方数据服务或铁路数据授权）；② 底图与发布环节通过地图合规审查。两条缺一不可。

09

验收标准

验收以「与 12306 官方口径比对」为核心，辅以性能与多端走查。逐项打勾后方可宣布交付完成。

指标目标值验收方式
