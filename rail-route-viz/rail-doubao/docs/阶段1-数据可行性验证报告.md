# 阶段 1 · 数据可行性验证报告

**项目**：rail-doubao（高铁动车路线图可视化平台）
**验证范围**：设计方案第 04 节「数据可行性验证」——试点**厦门北站**
**验证日期**：2026-09-22（实时抓取）；抽样补充日期 2026-09-23
**验证方式**：脚本自动化（`scripts/probe_czxx.py`，Python 标准库，低频节流）+ 真实浏览器复核（指纹受限环节）
**合规口径**：仅个人/内部低频研究演示；不复制、不发布、不商业使用（12306 使用条款约束）；请求节流 SLEEP_BASE=3s+随机抖动

## 3. 关键发现

### 3.1 电报码更正（主键风险实证）
官方字典实测：**厦门北 = XKS、厦门 = XMS、冠豸山 = GPS、冠豸山南 = GSS**。
此前第三方资料「厦门北 = XMS」为**误传**（XMS 实为厦门站）。方案中「电报码为主键、站名仅展示」的设计得到验证，按站名匹配会造成错站。

### 3.2 车站车次官方端点当前失效
`czxx/query` 在无头请求与真实浏览器（含页面自身 JS 发起的同源请求）中均返回 **404**。页面合并脚本 `czxxcx_js.js?scriptVersion=1.95052` 仍引用该路径，属前端/后端版本未同步。此环节是「指定站点始发/终到/途经全量车次」的官方唯一来源，当前不可用。

### 3.3 替代链路可用但有口径波动
`leftTicket/queryG`（站到站）与 `czxx/queryByTrainNo`（经停）均可无头访问。**注意**：queryG 返回的车次列表在多次请求间存在波动（同一天厦门北→杭州东返回 5–8 行不等，个别车次如 D3124 时有时无），推测与余票/缓存相关——官方 FAQ 亦声明「车票全部售罄后不再显示」。**结论：queryG 适合作经停/时刻的交叉来源，不适合作全量车次权威清单**。

### 3.4 无需验证码
`openRandCodeCheck='N'`：车站车次查询当前不校验验证码（页面仍加载验证码组件但未启用），脚本无需 OCR。

### 3.5 数据时效风险实例
G2372（厦门北→成都东）实时数据：**06:48 → 20:58，历时 14:10**（2026-09-23 运行）；
方案演示用公开资料（2026-07 检索）：20:33 到达。**到达时刻差 25 分钟** → 论证了「演示数据仅作示意、正式页面必须以实时数据为准」的必要性。

## 6. 可行性结论与影响评估

**可行**：会话、字典、站到站列表、经停序列、交叉校验均可用 → **地图可视化所需的数据模型（站点→车次→经停→时刻）可完整构建**，且全程可无头自动化、无需验证码。

**受限**：`czxx/query`（车站全量车次）服务端失效 → 「指定站点全部始发/终到/途经车次」的官方直取通道不可用。影响与候选方案：

| 方案 | 说明 | 评估 |
|---|---|---|
| A. 等官方恢复 | 前端包引用与后端映射不同步，可能随版本更新恢复 | 零成本，时间不可控；应设监控（定期探测） |
| B. 浏览器快照 | 用真实浏览器打开车站车次页（页面 JS 查询被 404 阻断，当前同样无数据） | **当前同样不可用**（本轮已实测浏览器内 404），不作为主选 |
| C. 第三方授权 API | 极速数据 `/api/train/`、易客 `/index/train` 等提供车站车次查询 | 需授权/费用；作为生产备选（方案已预留） |
| D. 站到站枚举重建 | 以 queryG 从目标站向多目标站枚举后去重 | 请求量大（与车站联通站数成正比）、且受余票隐藏影响，不推荐作全量 |

**建议**：阶段 2 以「经停序列 + 站到站」构建路线图主体（数据已验证），全量车次环节采用 C 方案兜底或 A 方案监控恢复；页面明确标注数据时间与口径。
