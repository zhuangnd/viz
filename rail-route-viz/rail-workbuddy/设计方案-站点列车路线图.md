# 指定站点高铁/动车路线图 — 数据收集与可视化页面设计方案

目标站点用 `X` 表示，方案对所有客运站通用，不绑定具体站点。

---

## 1. 目标与范围

| 项 | 内容 |
|---|---|
| 核心目标 | 地图可视化该站所有正在运营的高铁(G)、动车(D)、城际(C)线路的完整走向与站点时刻 |
| 三类结果 | 始发（X 为第 1 站）／到达（X 为末站）／经过（X 为中间停站） |
| 时间要素 | 每站的到达时间、发车时间、停留时长、区间运行耗时、距始发站累计耗时 |
| 交付形态 | 静态 HTML 页面 + 本地 JSON 数据，零构建、双击即开 |
| 非目标 | 不做余票查询、不做购票、不做票价、不涉及用户登录态数据 |

---

## 2. 数据源盘点

### 2.1 官方接口（真值源，用于核实"最新运营"）

| 接口 | 用途 | 返回关键字段 |
|---|---|---|
| `GET https://kyfw.12306.cn/otn/resources/js/framework/station_name.js` | 全量车站与三字电报码映射 | `站名\|拼音\|电报码`（文本，需自行解析） |
| `POST/GET https://kyfw.12306.cn/otn/leftTicket/query` | 站到站车次列表，取出 `train_no` | `station_train_code`、`train_no`、`from_station_telecode`、`to_station_telecode` |
| `GET https://kyfw.12306.cn/otn/czxx/queryByTrainNo` | **核心**。给定 `train_no` + 起终电报码 + 发车日期，返回该车次全部经停站点 | `station_no`、`station_name`、`arrive_time`、`start_time`、`stopover_time`、`train_class_name`、`start_station_name`、`end_station_name` |

`czxx/queryByTrainNo` 返回示例片段：

```json
{
  "status": true,
  "data": { "data": [
    { "station_no": "01", "station_name": "兰州", "arrive_time": "----",
      "start_time": "19:20", "stopover_time": "----",
      "station_train_code": "D858", "train_class_name": "动车",
      "start_station_name": "兰州", "end_station_name": "成都东" },
    { "station_no": "02", "station_name": "渭源", "arrive_time": "20:49",
      "start_time": "20:52", "stopover_time": "3分钟" }
  ]}
}
```

**会话要求**：请求前需先访问 `https://kyfw.12306.cn/otn/leftTicket/init` 建立会话并复用 Cookie，请求头带上 `Referer: https://kyfw.12306.cn/otn/leftTicket/init` 与常规 `User-Agent`，否则返回 `-1` 或空 `data`。

### 2.2 站点经纬度（官方接口不含此项）

`station_name.js` 只有电报码，**没有坐标**。坐标有三条获取路径：

| 方案 | 说明 | 推荐度 |
|---|---|---|
| A. 开源车站数据集 | 已有社区整理的带经纬度车站表（如各类 "全国火车站信息表"，字段含站名/电报码/省市/经纬度）。注意多为 **bd09 坐标**，需转 GCJ-02 | ★★★★★ 首选，一次性、离线、无配额 |
| B. 地图厂商 Web 服务「地点检索/地理编码」API | 用「XX站」关键字批量检索，返回 GCJ-02 坐标，准确且可纠偏 | ★★★★ 需申请 key，有日调用配额 |
| C. 手工补录 | 针对 A/B 均未命中的小站 | ★★★ 作为兜底 + 校验队列 |

**坐标系必须统一为 GCJ-02**。腾讯地图 GL JS 只吃 GCJ-02，bd09 直接用会偏移约 500m。

### 2.3 候选车次全集（用于反查"哪些车经过 X"）

这是唯一缺少官方直接接口的环节，见第 3 节。

## 3. 核心难点：如何找全"经过 X 的所有车次"

12306 只有「站→站」查询，**没有**开放的「按站查车次」接口。三条路径对比：

| 路径 | 做法 | 覆盖率 | 成本 | 结论 |
|---|---|---|---|---|
| **A. 全量车次库反查** | 先获得一份全量车次清单（`train_code → train_no + 起终站`），逐车次拉详情，筛出经停站含 X 的 | 高 | 一次性全量抓取（数千车次），之后每日增量 | **推荐** |
| B. 站到站穷举 | 以 X 为一端，遍历所有其他站做 `leftTicket/query` | 理论全覆盖 | 数千次查询，几乎必然触发风控，实际不可行 | 不推荐 |
| C. 限定范围穷举 | 只对某省/邻省/大站做站到站查询 | 低，漏车 | 中等 | 仅做补充校验 |

**推荐的 A 路径，候选全集两档：**

- **A1（省事）**：直接取社区每日更新的车次快照（`train_list_YYYYMMDD.json` / `train_detail_YYYYMMDD.json`），本地按站名过滤出候选 `train_no` 列表。优点是零风控风险，缺点是依赖第三方更新时效。
- **A2（自主）**：自己按车次等级（G/D/C）+ 数字前缀递归调用 `leftTicket/query` 建全集；单次返回少于 200 条即视为该前缀已穷尽。缺点是要自己管并发与失败重试。

**关键校正步骤**：候选集可能含已停运或改线车次。必须对每个候选 `train_no` 再打一次实时的 `czxx/queryByTrainNo`，**以实时返回是否为最新为真值**——并把"本次采集日期"明确标注在页面上。这一步不可跳过，否则"最新运营"无法保证。

## 4. 数据模型

四个平面文件，全部 UTF-8 JSON：

```
rail-route-viz/
├─ data/
│  ├─ stations.json        # 车站主数据
│  ├─ trains.json          # 候选车次全集（含 role 标记）
│  ├─ stop_times.json      # 逐车次逐站时刻（主表，最大）
│  └─ index-{站名}.json    # 前端实际消费的结果集
├─ etl/
│  ├─ fetch_stations.py
│  ├─ fetch_train_list.py
│  ├─ fetch_schedules.py
│  └─ build_dataset.py
└─ index.html
```

### stations.json

| 字段 | 类型 | 说明 |
|---|---|---|
| `telecode` | string | 电报码，主键，如 `WEI` |
| `name` | string | 站名规范字（去多余空格） |
| `city` / `province` | string | 行政区划 |
| `lng` / `lat` | float | **GCJ-02**，经度在前 |
| `coord_source` | enum | `dataset` / `api` / `manual`，便于质量追踪 |
| `same_city_stations` | string[] | 同城站，如 `["苏州园区","苏州新区","苏州"]` |

### trains.json

| 字段 | 说明 |
|---|---|
| `train_no` | 内部车次编号，主键，如 `240000G10281` |
| `train_code` | 显示车号，如 `G1028` |
| `train_class` | 高铁 / 动车 / 城际 |
| `start_station` / `end_station` | 始发 / 终到站名 |
| `role_for_X` | `origin` / `terminus` / `pass`（相对目标站） |
| `verified_date` | 最后一次实时核实成功日期 |
| `active` | bool，实时接口仍返回该车次则为 true |

### stop_times.json（每行 = 一个车次的一个停车站）

| 字段 | 来源/算法 |
|---|---|
| `train_no`, `station_no` | 原始 |
| `station_name`, `telecode` | 原始 + 站名反查电报码 |
| `arrive_time`, `depart_time` | 原始 `arrive_time` / `start_time`，`----` 归一为 `null` |
| `stopover_min` | 解析 `stopover_time`（"3分钟" → 3），`----` → 0 |
| `day_offset` | 跨天数，算法见 5.1 |
| `is_stop` | 该车次是否在此站办理客运（避免把"通过不停车"误算成站点） |
| `segment_min` | 与上一站之间的运行耗时 |
| `cum_min` | 距始发站累计运行分钟 |
| `segment_km` / `cum_km` | 相邻站直线距离（Haversine），**估算值** |
| `lng` / `lat` | 冗余落一份，前端免二次 join |

### index-{站名}.json（前端唯一输入）

```json
{
  "meta": { "station": "XX站", "capture_date": "2026-09-22",
            "source": "12306", "coord_type": "GCJ-02",
            "note": "直线距离估算，非运营里程" },
  "summary": { "total": 128, "origin": 5, "terminus": 4, "pass": 119,
               "g": 96, "d": 28, "c": 4, "unique_cities": 63 },
  "target": { "telecode": "XXX", "lng": 116.4, "lat": 39.9,
              "peak_hour_distribution": [/*24 桶*/] },
  "trains": [ { "train_no": "...", "train_code": "G1234",
                "role": "pass", "arrive_at_X": "14:32",
                "depart_at_X": "14:34", "stopover_min": 2,
                "total_min": 268, "path": [[lng,lat], ...],
                "stops": [ { "station_no":"01", "name":"...",
                             "arrive":null, "depart":"08:00",
                             "stopover_min":0, "segment_min":0,
                             "cum_min":0, "cum_km":0 } ] } ]
}
```

## 5. 派生字段计算规则

### 5.1 跨天数（`day_offset`）

原始接口只给 `HH:MM`，不给运行天数。规则（逐站向后扫描，携带一个 `cur_day = 0`）：

```
if arrive is not None:
    if arrive_min < prev_depart_min and (prev_depart_min - arrive_min) > 720:
        cur_day += 1        # 跨过午夜，且不是因为"到站早于发车"的正常序列
    arrive_abs = cur_day * 1440 + arrive_min
if depart is not None:
    if prev_depart is not None and depart_min < prev_depart_min:
        cur_day += 1
    depart_abs = cur_day * 1440 + depart_min
```

要点：**逐相间时间若 > 12 小时也需人工复核**（可能是数据异常，也可能是真·长区间）。所有 `cur_day > 0` 的记录应输出到一个 `cross_midnight_review.csv` 供抽查。

### 5.2 区间与累计耗时

```
depart_at_X = depart_abs - start_depart_abs         # 目标站在全线的时间位置
segment_min = arrive_abs[i] - depart_abs[i-1]       # 纯运行时间，不含前站停站
stopover_at_X = depart_abs - arrive_abs             # 目标站停留
cum_min       = depart_abs - depart_abs[0]          # 距始发累计（含停站）
```

UI 上必须区分两个口径，别混着显示：**区间运行耗时**（两站之间在路上的时长）vs **行程累计时长**（含停站）。

### 5.3 距离估算

相邻站 Haversine 直线距离。务必在页面脚注标明"直线距离，非铁路运营里程，实际里程通常长 8%~25%"，不要把它标榜为"里程"。

### 5.4 角色判定

```
role = 'origin'   if station_no == '01'
role = 'terminus' if 是该 train_no 的最后一站
role = 'pass'     otherwise
```

个别车次在同一条线上会有重名站（少见），需以 `train_no + station_no` 为唯一键而非站名。

## 6. 采集纪律（避免风控与合规风险）

| 项 | 做法 |
|---|---|
| 并发 | 单 IP 并发 ≤ 3，每个任务随机延迟 300~900ms |
| 重试 | 失败入队重排，最多 3 轮，指数退避 |
| UA | 从池子里随机取，不用单一固定 UA |
| 频次 | 全量只做一次；日常增量每天 1 次即可，不需要高频 |
| 数据边界 | **只取公开时刻表**，不碰余票、不碰票价、不碰任何实名/账户数据 |
| 用途声明 | 页面显著位置标注数据来源 12306 与采集日期，仅供个人学习研究，不可商用分发 |
| 站点许可 | 这是对方服务器的资源，单租户自用、低频请求即合理边界；不要做成对外服务 |

## 7. 可视化页面设计

### 7.1 技术选型（受地图合规约束）

| 层 | 选型 | 理由 |
|---|---|---|
| 底图 | **腾讯地图 GL JS**（SDK 从官方 CDN 加载，走本地代理，前端零 key） | 大陆地图必须只用持牌厂商：腾讯 / 高德 / 百度 / 天地图 |
| 禁用的 | Leaflet + OSM、Mapbox、Google/Apple/Bing 海外版 | 未取得国内测绘资质，不可用于国内地图渲染 |
| 线路 | `TMap.MultiPolyline` | 一条车次一条 `polyline` |
| 站点 | `TMap.MultiMarker` + 内联 SVG 图标 | 不能用官方 demo 图片路径 |
| 图表 | 原生 SVG/Canvas，不引图表库 | 保持零构建、零依赖 |
| 页面 | 单 HTML + 原生 JS，ES Module | 同现有 project 风格，双击即开 |

底图不做自定义样式（`mapStyleId`），容器必须有显式高度（如 `height: 100vh`），否则地图渲染不出来。

### 7.2 地图要素

- **目标站**：红色大号 marker，始终在最上层，初始 `center` 锁定它
- **沿途站点**：蓝色小圆点；三种站点进一步用形状/颜色区分 始发 ▲ / 终到 ▼ / 经停 ●
- **选中线路**：高亮加粗 + 抬升 `zIndex`；未选中线路降到低透明度，避免几十条线糊成一团
- **初始视图**：默认只渲染 `role != pass` 的一部分或全部 G/D；提供"全部显示"开关。120+ 条线同屏必须靠淡化，不能靠移除
- **连线性质**：相邻站点直线连接，**示意性的拓扑走向，不是真实线位**。跨海/穿越山脉的大区间直线要在脚注里说明

### 7.3 交互

| 交互 | 行为 |
|---|---|
| 点击线路 | 高亮该线路 + 其余淡化 + 右侧展开完整时刻表 + 地图自动 `fitBounds` |
| 点击站点 marker | Tooltip：站名 + 有多少车次经过 + 该站在选中车次上的到/开时刻 |
| 点击时刻表某一行 | 地图定位到该站并高亮 |
| 顶栏筛选 | 车次类型 G/D/C、role（始发/到达/经过）、是否只在目标站停车 ≤ N 分钟 |
| 排序 | 按到达 X 的时间升序（把一天的到发分布拉成时间轴视图） |
| 同城站切换 | X 与同城站快速互换（如"苏州" ↔ "苏州北"），这是实际使用中最高频的需求 |
| 键盘 | ↑↓ 逐条切换线路，Esc 取消选中 |

### 7.4 侧栏内容

1. **目标站概览卡**：始发 N / 到达 N / 经过 N，最早/最晚一班时间，通达城市数
2. **时刻分布**：24 小时柱状图，直观看出该站的到发潮汐
3. **车次列表**：车号、起终站、在 X 的到/开/停、全程时长
4. **选中车次时刻表**：站序｜站名｜到达｜发车｜停留｜**区间耗时**｜**累计耗时**｜累计直线距离，目标站那一行底色高亮

## 8. 实施步骤

| 阶段 | 产出 | 验收标准 |
|---|---|---|
| P1 数据底座 | `stations.json` | ≥ 3000 客运站，GCJ-02 坐标命中率 > 97%，未命中的入人工队列 |
| P2 候选集 | `trains.json` | 拿到 G/D/C 全量 `train_no`，去重后条数对数并核对不会大量缺失 |
| P3 实时核实 | `stop_times.json` | 逐个候选打 `czxx`，失败 < 2%；标记 `active` / `inactive` |
| P4 派生计算 | 补齐 `day_offset` / `segment_min` / `cum_min` / `cum_km` | 抽查 20 条跨夜车次，累计耗时与 12306 页面显示一致 |
| P5 结果集 | `index-{站名}.json` | JSON 可被浏览器直接 fetch，体积 < 3MB（超限则压缩为 MessagePack 或按车次分片加载） |
| P6 页面 | `index.html` | 地图正常出图、能筛选、能点线路看时刻表 |
| P7 固化 | 把 X 参数化 | 换一个站名重跑即可，不需要改代码 |

## 9. 风险清单

| 风险 | 影响 | 应对 |
|---|---|---|
| 12306 接口改版（`query` 曾变 `queryA`/`queryZ`） | 采集中断 | 封装一层 adapter，接口地址集中在一处配置；失败时快速定位是"改版"还是"风控"（返回体不同） |
| 触发风控导致封 IP | 采集中断 | 严格按第 6 节限流；优先走候选快照降低请求量 |
| 调图导致数据过期 | 页面显示过时时刻表 | 页面顶部强制显示采集日期；支持重新跑 ETL 覆盖更新 |
| 周末/高峰运行图不同 | 时刻表在某个日期不成立 | 采集时用 3 个不同星期几做交叉验证，不一致的在 UI 上打标"运行图有差异" |
| 直线距离误导用户 | 被当成"里程"引用 | 明确命名"直线距离(估算)"，不是"里程" |
| 数据体积过大 | 页面加载慢 | `role` 分档加载：先加载在 X 的事实行 + `path` 坐标，完整时刻表点开再加载 |
| 地图合规 | 底图/边界问题 | 只用腾讯地图官方底图，不自行绘制或上传任何国界/行政区划边界数据 |
