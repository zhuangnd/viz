## 一、案例：报关单出口贸易增长乏力，怎么看？

业务原话：

> "今年出口贸易增长乏力，得查查怎么回事。"

——这跟"这个月费用怎么这么高"是同款含糊：**带情绪、有方向、没动作**。我们按文档的总路径走：

> **结构化思维（分析信息）→ 问题模型 → 工程化思维（设计系统）→ 系统解决方案**

落地为三个车间，**最后一个车间就是 SQL**。

---

## 二、车间一：拆开看 —— 结构化思维 → 问题模型

**思维工具**：结构化思维 —— 分解、分类、构建逻辑关系。
**产出**：问题模型 —— 一个解释问题逻辑结构的简单公式（"一个用来理解复杂问题的简单框架或公式"，文档原话）。

### 2.1 三步拆解

1. **跟谁比？** —— 跟去年同期比、跟全国均值比、跟兄弟关比。
2. **乏力在哪？** —— 国家、HS 大类、企业主体、贸易方式，至少四个维度。
3. **为什么乏力？** —— 量（报关单数、货值、吨数）还是价（单价），还是结构变了。

### 2.2 拼出公式（问题模型）

```
出口贸易额 = Σ 各 HS 编码 × 单价 × 数量
同比增长率 = (本期贸易额 − 同期贸易额) ÷ 同期贸易额
乏力归因 = 量贡献 + 价贡献 + 结构贡献
```

> 这就是文档说的"问题模型"——"增长 = 市场规模 × 市场份额"的海关版。
> 此刻**一个数字都没有**，但问题已经被"拆开、说清"。这一步用的是结构化思维，解决"如何看清问题"。

### 2.3 一个常见错：拆不全

| 拆法 | 是否到位 | 后果 |
|---|---|---|
| 只看总额 | ❌ | 越看越糊涂，不知力在哪 |
| 拆到 HS 大类 | ✅ | 能定位"哪类产品乏力" |
| 拆到 HS 大类 + 国别 + 企业 + 贸易方式 | ✅✅ | 能定位"哪类企业 / 哪国 / 哪种贸易方式" |

**拆到什么程度算够？——拆到"能落到一张表的一个字段"为止。** 拆到这，问题模型就可以交给车间二了。

## 三、车间二：找着数 —— 工程化思维 → 信息模型

**思维工具**：工程化思维 —— 问题可定义（输入/输出/约束）、系统设计（模块化）。
**产出**：信息模型 —— 组织数据的结构（数据库表设计）。

### 3.1 把公式里的变量，落到海关的"业务表"

| 问题模型里的变量 | 数据落在哪（信息模型） | 口径坑 |
|---|---|---|
| 贸易额 | 报关单 × 总价（统计美元价） | 用 `美元` 还是 `人民币`？是否含运保费？ |
| 数量 | 报关单 × 数量 + 法定单位 | 散货 / 整柜 / 第二计量单位怎么折？ |
| HS 编码 | 报关单 × 商品编码（前 4 位 / 6 位 / 8 位） | 拆到几位看问题？ |
| 出口主体 | 报关单 × 经营单位代码 + 关联企业 | 含不含跨境电商、海外仓？ |
| 同期数据 | 历史库 | 行政区划调整过没有？编码版本换过没有？ |
| 异常筛除 | 报关单 × 状态 + 担保标志 | 含不含"已删单"？"异常补税"？ |

### 3.2 信息模型速记图

```
[报关单主表]──┬──[商品归类表] (HS编码 → 大类名)
              ├──[企业备案表] (经营单位代码 → 企业名/规模)
              ├──[国别代码表] (目的国 → 区域)
              └──[历史归档表] (按月分区,上年同期)
```

> 这一步的产出是信息模型——文档原话"组织数据的结构（如：数据库表设计）"。用的已经是工程化思维：输入/输出/约束明确、模块化、可定义。

### 3.3 工程化思维的三条自检

1. **可定义**：每张表的主键、每字段的口径，能写进字段说明表吗？
2. **模块化**：本期 vs 同期、总额 vs 明细，能分两表 join 而不交叉冗余吗？
3. **可约束**：筛除条件、关联规则、关联缺失处理，能写成 if-else 决策树吗？

## 四、车间三：算出来 —— 工程化思维 → 数学模型（**= SQL**）

**思维工具**：工程化思维 —— 可验证、迭代。
**产出**：数学模型 —— 用于预测或计算的数学公式（这里就是 **SQL 语句**）。

> 文档原话：方法服务于问题——**能一条 SQL 说清的，不上机器学习**。这句话在海关数据场景里尤其要命。

### 4.1 同比增长率（一条 SQL）

```sql
-- 业务问题："今年累计同比，去年累计同比，差多少？"
WITH y AS (
  SELECT SUM(total_price_usd) AS sum_y, COUNT(*) AS cnt_y
  FROM   customs_declaration
  WHERE  ie_flag = 'E'                  -- 出口
    AND  decl_date BETWEEN '2025-01-01' AND '2025-08-31'
),
c AS (
  SELECT SUM(total_price_usd) AS sum_c, COUNT(*) AS cnt_c
  FROM   customs_declaration
  WHERE  ie_flag = 'E'
    AND  decl_date BETWEEN '2026-01-01' AND '2026-08-31'
)
SELECT
  ROUND((c.sum_c - y.sum_y) / y.sum_y * 100, 2) AS yoy_pct,
  ROUND((c.cnt_c   - y.cnt_y) / y.cnt_y * 100, 2) AS cnt_yoy_pct;
```

### 4.2 结构归因（量 × 价 × 结构）

```sql
-- 业务问题："增长乏力，主要是量掉了，还是价掉了，还是结构变了？"
SELECT
  hs4,
  hs4_name,
  -- 价贡献：本年均价 − 上年均价 × 本年数量
  ROUND(SUM(avg_price_c - avg_price_y * qty_c) / y_total * 100, 2) AS price_contrib,
  -- 量贡献：本年数量 − 上年数量 × 上年均价
  ROUND(SUM((qty_c - qty_y) * avg_price_y) / y_total * 100, 2)     AS qty_contrib,
  -- 结构贡献（HS 占比变化）已通过加权分摊到上两列
  ROUND(SUM(total_c) - SUM(avg_price_y * qty_c), 2)                 AS struct_contrib
FROM   ...
GROUP  BY hs4, hs4_name
ORDER  BY ABS(price_contrib + qty_contrib + struct_contrib) DESC
LIMIT  20;
```

### 4.3 找异常单位（监督视角）

```sql
-- 业务问题："哪些经营单位 / 哪些 HS，下滑远超行业均值，疑点最大？"
WITH base AS (
  SELECT decl_company, hs4,
         SUM(CASE WHEN year=2026 THEN total_price_usd END) AS v_c,
         SUM(CASE WHEN year=2025 THEN total_price_usd END) AS v_y
  FROM   customs_declaration
  WHERE  ie_flag = 'E' AND year IN (2025,2026)
  GROUP  BY decl_company, hs4
)
SELECT *,
       ROUND((v_c - v_y) / NULLIF(v_y,0) * 100, 2) AS yoy_pct,
       (v_c - v_y) / NULLIF(v_y,0) - (-0.03)       AS gap_vs_industry
FROM   base
WHERE  v_y > 1000000          -- 筛掉噪点小户
ORDER  BY gap_vs_industry ASC  -- 下滑最猛
LIMIT  50;
```

### 4.4 选 SQL 还是上 ML？——一条判断线

| 场景 | 工具 | 原因 |
|---|---|---|
| 同比 / 占比 / 排名 / 阈值 | **SQL** | 1 条 SQL 写得清、跑得快、审得过 |
| 异常模式挖掘 | 仍是 SQL + 简单统计量 | 多数"异常"用 z-score / IQR 就够 |
| 真要预测、聚类、文本相似 | 才上机器学习 | 数据足够、问题足够复杂、值不上当 |

> 文档原话："方法服务于问题——能一条 SQL 说清的，不上机器学习。"
> 海关联检/监督场景里，SQL 还多一个好处：**可解释、可复核、可留痕**——审委会不会看梯度下降，但看得懂 SELECT-WHERE-GROUP BY。

## 五、一条线看全：三种模型形态的接力

| 接力棒 | 车间 | 思维工具 | 产出长相 | 海关版的"人话" |
|---|---|---|---|---|
| 业务问题 | — | — | "出口贸易增长乏力" | 一句含糊的话 |
| → **问题模型** | 车间一 | 结构化思维 | 贸易额 = Σ HS × 单价 × 数量 | 把问题拆开、说清 |
| → **信息模型** | 车间二 | 工程化思维 | 报关单 / 商品归类 / 企业 / 国别 / 历史库 | 公式里每个数去哪张表找 |
| → **数学模型 = SQL** | 车间三 | 工程化思维 | 同比 SQL、归因 SQL、异常 SQL | 怎么把答案算出来 |
| → 业务结论 | 收尾 | 沟通（汇报三步法） | "前三 HS 大类量价齐跌，结构未变" | 一句业务听得懂的话 |

**注意开头和结尾都是"业务话"——模型（包括 SQL）只是中转站。**
进去的是业务问题，出来的必须是业务能用的结论。

## 六、转化的"方言对照表"（海关版）

业务话天然含糊，模型话必须精确。日常功课就是这张对照表的翻译：

| 业务怎么说（海关版） | 模型 / SQL 需要什么 |
|---|---|
| "增长乏力" | 基准（跟谁比）、幅度（低多少）、维度（按国家/HS/企业/贸易方式） |
| "今年明显不如去年" | 同比窗口、统计口径（人民币 / 美元）、是否含跨境电商 |
| "感觉某地流失严重" | "流失"的定义：转关？还是转港？转去哪个关区？ |
| "重点关注这几家" | 排序规则、TOP N、阈值（按绝对额？还是按 yoy_pct？） |
| "这事儿挺严重" | 严重程度的量化标尺（同比下滑 ≥ 30%？绝对额 ≥ 1 亿美元？） |
| "查一下" | 时间窗、范围、筛除条件、输出列、保密级别 |

**翻译不动的地方，就是要跟业务当面聊的地方——这本身就是需求澄清。**

## 七、回译检验：汇报三步法（海关场景）

转化是否成功，不看 SQL 多漂亮，看**能不能翻回业务话**。
《总结摘要》给的"经典汇报三步法"原话：

> "我们先把问题拆开来看（拆解）→ 从结构上可以用一个简单模型理解（公式）→ 因此解决路径主要分为三步（方案/工程化）。"

套到海关例子里，对着领导/业务部门这样讲：

### 第一步：拆解（结构化思维）

> "增长乏力，拆开看，主要来自 **三个维度**：
> 按 HS 大类分，机电产品占出口 60%，但今年前八月同比 -4.2%，是主力拖累；
> 按国别分，对东盟 +12%，对欧美 -8%，**结构在悄悄切换**；
> 按企业分，中小企业（出口额 < 5000 万美元）下滑 -15%，头部企业反而 +6%，**集中度在上升**。"

> 这一句对应文档里的"拆解结构"模板："这个问题主要由三个因素/部分组成。"

### 第二步：模型（问题模型 + 数学模型）

> "用 **贸易额 = 量 × 价 × 结构** 一拆：
> 量贡献 -2.1 个百分点、价贡献 -1.5 个百分点、结构贡献 +0.4 个百分点。
> 翻译成业务话——**量价齐跌是主因，结构升级是亮点**。"

> 这一句对应"公式/模型结构"模板："这个业务可以用一个简单公式/框架来理解。"

### 第三步：方案（工程化思维）

> "建议下一步分 **三条线**核实：
> ① 查机电产品前十大 HS 编码的量价明细，看是订单转移还是价格战；
> ② 拉头部企业新增客户清单，看集中度上升是产业升级还是订单聚集；
> ③ 抽样 5 家中小出口企业，了解是资金压力还是汇率/关税问题。"

> 这一句对应"方案结构"模板："针对这个问题，我们有三个解决方向。"

### 业务点头了，转化才算完成闭环

反过来，如果只能念 `yoy_pct`、说不成人话，说明翻译链在半路断了——
SQL 解决了"好下手的问题"，没解决"真问题"。

## 八、五种汇报模板 · 一图速记

| 模板 | 业务原话 | 对应思维 | 对应车间 |
|---|---|---|---|
| 拆解结构 | "问题主要由三个因素组成" | 结构化思维 | 车间一 |
| 公式结构 | "可以用一个简单模型/框架来理解" | 问题模型 | 车间一 → 二 |
| 因果结构 | "主要原因有三个" | 归因 SQL | 车间三 |
| 流程结构 | "整个方案分为四步" | 工程化路径 | 车间三 → 收尾 |
| 方案结构 | "我们有三个解决方向" | 工程化思维 | 收尾 |

汇报时**不要直接说"我用了结构化思维"**——
把方法论翻成"三个因素 / 一个公式 / 三步方案"这种**业务听得懂的句子**，这本身就是结构化思维的最高段位。

## 九、四层抽象框架 · 给领导看的"自检表"

文档给了"四层抽象"——**任何复杂的思维方法/工具/系统，都可以从这四层讲清楚**。
套到"海关业务→SQL 数据建模"上，对应是这样的：

| 层级 | 海关业务→SQL 建模里的样子 |
|---|---|
| 事实层（看到什么） | 领导桌上那张"出口同比 -3.6%"的报表、SQL 跑出来的 50 行异常清单 |
| 功能层（在做什么） | 把"增长乏力"翻译成可计算、可复核的数字 |
| 逻辑层（怎么运作） | 三车间：拆解 → 找数 → SQL；信息模型 = 报关单主表 + 五张维表 |
| 原理层（为什么有效） | 短期记忆分块降低认知负担（结构化）；输入/输出/约束让系统可复用（工程化） |

汇报时，**先讲事实层（结论），再讲功能层（为什么要分析），再讲逻辑层（怎么做的），原理层留到被追问时**。
这也是 slide/20260910.html 演示页推崇的金字塔顺序——结论先行、论据跟上、机制垫底。

## 十、一图总结

```
  业务话："出口增长乏力"              业务话："量价齐跌，结构升级"
     │                                       ▲
     ▼   车间一(结构化)                       │
┌─────────┐   车间二(工程化)   车间三(工程化)  │
│ 拆开看   │ → │ 找着数   │ → │ 算出来(SQL) │─┘  回译：汇报三步法
└────┬────┘   └────┬────┘   └────┬────┘
     ▼             ▼             ▼
   问题模型       信息模型       数学模型
 (贸易额=HS×   (报关单/商品/  (同比SQL /
  单价×数量)    企业/国别/历史)  归因SQL /
                                异常SQL)
```

**记住四句话：**

1. **模型 = 一张只回答你这个问题的小地图**（文档原话），SQL 也是地图；
2. **转化 = 三个车间的接力**：拆开看（结构化）→ 找着数（工程化）→ 算出来（工程化）；
3. **能一条 SQL 说清的，不上机器学习**——海关场景里更要看重可解释、可复核、可留痕；
4. **转化的验收标准是回译**：汇报三步法——拆解 → 模型 → 方案，业务能点头，才算数。
