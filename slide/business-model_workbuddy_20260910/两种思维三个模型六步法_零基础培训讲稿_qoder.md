# 两种思维 · 三个模型 · 六步走通 —— 零基础 SQL 学员培训讲稿

> **培训对象**：数据分析零基础学员（不会写 SQL，但有业务经验）
> **核心主张**：SQL 不是最难的部分，想清楚才是。
> **贯穿案例**：慢案例——"出口增长乏力"；快案例——"昨天发生了什么？"
> **预计时长**：60–90 分钟（含学员练习）

---

## 模块 0：开场 —— 为什么是你，不是 AI

### 0.1 一个问题

各位同事，开始之前先问一个问题：

> **如果 AI 能写 SQL，你为什么还要学？**

这个问题很多人心里有。确实，现在让 AI 写一段 `SELECT ... GROUP BY`，几秒钟就出来了。那我们还坐在这里干什么？

### 0.2 一个真实故事

我先讲一件自己遇到的事。

有一次我让 AI 帮我查一份文件的依据。它给我引了一段——文号、日期、原文，一应俱全，格式完美。我回头一核：**文号不存在，日期对不上，整段是它现场编的。** 语气之诚恳，让我差点就信了。

这就是 AI 的特点：**它什么都敢说，但它什么都不负责。**

数字它不负责，结论它不负责，出了问题它更不负责。**它敢说，你敢签吗？**

### 0.3 一把尺子：五懂一具备

所以答案很清楚：AI 写得了代码，**判不了对错**。判对错靠什么？靠你自己的本事。

我们有一把老尺子，叫**"五懂一具备"**：

| # | 懂什么 | 一句话 |
|---|---|---|
| 1 | **懂业务** | 知道问题从哪来、风险藏在哪儿 |
| 2 | **懂系统** | 知道数据躺在哪个系统、怎么流转 |
| 3 | **懂技术** | 能把数据弄出来、洗干净、摆整齐 |
| 4 | **懂数据** | 知道字段的口径、质量、坑在哪儿 |
| 5 | **懂分析** | 把数据变成证据，把证据变成判断 |
| 6 | **沟通协调** | 分析做得再好，讲不明白等于零 |

这五懂串起来，正好是一条完整的路：

> **业务出题 → 系统找数 → 技术取数 → 数据验数 → 分析答题 → 沟通交卷**

大家发现没有——**中间四步，AI 都能帮忙提速；但第一步"出题"和最后一步"交卷"，AI 替不了你。** 业务越扎实，你越知道该问它什么；分析越扎实，你越知道它答得对不对。

**五懂越硬，AI 越是利器；五懂越虚，AI 越是隐患。**

这个班，练的就是五懂中间那三段——从"业务出题"到"沟通交卷"的翻译能力。

## 模块 1：思维工具箱 —— 2 种思维 + 3 个模型

在进入具体步骤之前，我们先把"武器"摆上桌。后文出现的所有概念，都从这里出发。

### 1.1 两种思维

| 思维 | 一句话 | 解决什么 | 四个动作/特征 |
|---|---|---|---|
| **结构化思维** | 把含糊的问题拆开看、说清楚 | 如何**看清**问题 | 分解、分类、构建逻辑关系、可表达 |
| **工程化思维** | 把想法变成能落地、能验证的步骤 | 如何**改变**现实 | 可定义（输入/输出/约束）、模块化、可验证、迭代 |

**一句话记住**：结构化思维让你"看懂题"，工程化思维让你"做对题"。做分析，两种要交替使用。

### 1.2 三个模型

"模型"这个词听着吓人，但在我们这里，它的意思很简单——**一个解释问题的简单框架**。

| 模型 | 一句话 | 产出长什么样 | 在本课对应什么 |
|---|---|---|---|
| **问题模型** | 一个理解问题的简单公式 | 白纸上的公式 | 步骤 1 拆出来的"贸易额 = Σ HS × 单价 × 数量" |
| **信息模型** | 数据在哪张表、什么口径 | 表关系图 | 步骤 2 画出来的"报关单主表 + 4 张维表" |
| **数学模型** | 把答案算出来的方法 | 一条能跑的 SQL | 步骤 3 拖出来的节点链路 |

**速记口诀**：问题模型 = 公式；信息模型 = 表格；数学模型 = SQL。

### 1.3 三种模型是接力的

```
业务问题（含糊的话）
    ↓ 结构化思维
问题模型（把问题拆开、说清）
    ↓ 工程化思维
信息模型（公式里每个数，去哪张表找）
    ↓ 工程化思维
数学模型 = SQL（怎么把答案算出来）
    ↓ 回译
业务结论（业务听得懂的话）
```

**注意开头和结尾都是"业务话"**——模型只是中转站。进去的是业务问题，出来的必须是业务能用的结论。

**跳过任何一个模型，后面都站不住。** 没拆清楚就找数，会找错；没找到数就建模，会建歪。

## 模块 2：六步法全图 —— 先看终点再走路

### 2.1 一张全景图

```
业务话 → ① 拆解 → ② 找数 → ③ 建模 → ④ 验证 → ⑤ 分析 → ⑥ 报告 → 业务结论
```

| 步骤 | 做什么 | 用什么思维 | 产出什么 |
|---|---|---|---|
| ① 拆解 | 把含糊的业务话拆成几块，拼成公式 | 结构化 | 问题模型（白纸上的公式） |
| ② 找数 | 公式里的变量，对应到哪张表哪个字段 | 结构化→工程化 | 信息模型（表关系图） |
| ③ 建模 | 在工具里拖节点，拼出能跑的查询 | 工程化 | 数学模型（可视化 SQL 链路） |
| ④ 验证 | 行数、空值、极值、抽样回查 | 工程化 | 验证清单（对得上/对不上） |
| ⑤ 分析 | 在验证过的数据上分组、排序、算贡献 | 工程化→结构化 | 表 + 图 + 三句话 |
| ⑥ 报告 | 用汇报三步法讲回业务话 | 结构化 | 一页纸结论 |

### 2.2 两种思维的节拍

- **1 → 2** 走结构化（看清问题）
- **3 → 4 → 5** 走工程化（建系统 + 验 + 用）
- **6** 回到结构化（讲明白）

两种思维交替出现，缺一不可。

### 2.3 一句话定调

> **新手不是不会分析，是不会写 SQL 代码。** 所以我们用"拖拽式 SQL"——把代码变成乐高积木，每个节点就是一段 SQL，连起来就是一条能跑的查询。**你拖的不是花哨的可视化，是 SQL 代码本身。**

但——**拖拽只是省了"写字"，省不了"想清楚"。** 拖什么节点、怎么连、按什么顺序，全靠两种思维撑起来。

## 模块 3：慢案例走完全程 —— "出口增长乏力"

下面我们用一句业务话，从头走到尾。

### 步骤 1：拆解（结构化思维 → 问题模型）

> **这一阶段不进工具。** 拿白纸或 Word 写就行。

#### 业务原话

> "今年出口贸易增长乏力，得查查怎么回事。"

这跟"这个月费用怎么这么高"是同款含糊：**带情绪、有方向、没动作。**

#### 三个拆解动作

| 问什么 | 海答案例 | 为什么重要 |
|---|---|---|
| **跟谁比？** | 跟去年同期比 / 跟全国均值比 / 跟兄弟关比 | 没有基准，"乏力"二字就站不住 |
| **乏力在哪？** | 国家、HS 大类、企业主体、贸易方式 | 不拆维度，永远在原地打转 |
| **为什么乏力？** | 量（单数/货值/数量）？价（单价）？结构变了？ | 拆因才能拆方案 |

#### 拼成公式（问题模型）

```
出口贸易额 = Σ 各 HS 编码 × 单价 × 数量
同比增长率 = (本期贸易额 − 同期贸易额) ÷ 同期贸易额
乏力归因   = 量贡献 + 价贡献 + 结构贡献
```

此刻**一个数字都没有**。但问题已经被"拆开、说清"了。这就是问题模型——一个用来理解复杂问题的简单框架。

#### 自检：拆到什么时候停？

**拆到"能落到一张表的一个字段"为止。** 比如"按 HS 大类"还不够——HS 大类存在哪张表的哪个字段？想到了，就停笔，进步骤 2。

#### 一个常见错：拆不全

| 拆法 | 是否到位 | 后果 |
|---|---|---|
| 只看总额 | ❌ | 越看越糊涂，不知力在哪 |
| 拆到 HS 大类 | ✅ | 能定位"哪类产品乏力" |
| 拆到 HS 大类 + 国别 + 企业 + 贸易方式 | ✅✅ | 能定位"哪类企业/哪国/哪种贸易方式" |

---

### 步骤 2：找数（结构化 → 工程化 → 信息模型）

> 这一步要进工具了，但**只是摸数据，不动计算**。

#### 把公式里的变量，翻译成"数据在哪儿"

| 公式里的变量 | 数据落在哪 | 口径坑 |
|---|---|---|
| 贸易额 | 报关单 × 总价（统计美元价） | 用美元还是人民币？含运保费吗？ |
| 数量 | 报关单 × 数量 + 法定单位 | 散货/整柜/第二计量单位怎么折？ |
| HS 编码 | 报关单 × 商品编码（前 4/6/8 位） | 拆到几位看问题？ |
| 出口主体 | 报关单 × 经营单位代码 | 含不含跨境电商、海外仓？ |
| 同期数据 | 历史归档表 | 行政区划调整过没？编码版本换过没？ |
| 异常筛除 | 报关单 × 状态 + 担保标志 | 含不含"已删单"？"异常补税"？ |

#### 在工具里做什么？

拖一个"数据源"节点，配置成：

```
[数据源节点：报关单]
   ├── 来自：报关单主表
   ├── 关联：商品归类表（按 HS 编码）
   ├── 关联：企业备案表（按经营单位代码）
   ├── 关联：国别代码表（按目的国）
   └── 关联：历史归档表（按月份）
```

这就是信息模型——"组织数据的结构"。

#### 零基础最常犯的错

**❌ 错**：上来就拖【过滤】【聚合】节点，数据从哪来都没搞清楚。
**✅ 对**：先把表关系画清楚，再用工程化的态度进工具。

---

### 步骤 3：建模 —— 拖拽式 SQL 核心（工程化思维 → 数学模型）

> **这是培训的核心。** 新手不会写 SQL，那就把 SQL 拆成节点，一个一个拖。

#### 一句话理解"拖拽式 SQL"

**普通 SQL 代码**：

```sql
SELECT hs4, SUM(total_price_usd) AS sum_c
FROM   customs_declaration
WHERE  ie_flag = 'E'
  AND  decl_date BETWEEN '2026-01-01' AND '2026-08-31'
GROUP  BY hs4
ORDER  BY sum_c DESC
LIMIT  20;
```

**拖拽式 SQL（同一段查询的"节点形态"）**：

```
[数据源：报关单]  →  [过滤：出口 + 2026-01-01~2026-08-31]
                              ↓
                   [聚合：按 hs4 分组, SUM(总价)]
                              ↓
                   [排序：按 sum_c 降序]
                              ↓
                     [行数限制：前 20 行]
```

**每个节点 = 一段 SQL 代码，你只是没看见它。** 工具会自动拼成上面那段 `SELECT-WHERE-GROUP BY`。

#### 节点 ↔ SQL 对照表

| 节点 | 等价 SQL | 主要思维 |
|---|---|---|
| ① 数据源 | `FROM customs_declaration JOIN ...` | 工程化：把所有可能用到的表摆上桌 |
| ② 过滤 | `WHERE ie_flag='E' AND decl_date BETWEEN ...` | 结构化：把不符合口径的一刀切掉 |
| ③ 聚合 | `GROUP BY hs4 ... SUM(total_price)` | 结构化：把明细压缩成口径一致的合计 |
| ④ 计算列 | `SELECT ..., (v_c-v_y)/v_y AS yoy_pct` | 工程化：把业务关心的派生指标算出来 |
| ⑤ 过滤 | `WHERE v_2025 > 100万` | 工程化：把噪点剔掉，让结论站得住 |
| ⑥ 排序+行数限制 | `ORDER BY yoy_pct ASC LIMIT 50` | 结构化：把答案按业务可读的方式排出来 |

#### 海关版完整 6 节点链路

```
① [数据源：报关单]   ← 步骤 2 配好的主表 + 4 张维表
        ↓
② [过滤]             ← ie_flag = '出口' AND 时间窗 IN (2025年, 2026年)
        ↓
③ [聚合]             ← 按 hs4, dest_country, decl_company 分组
                       SUM(总价美元) AS v, COUNT(*) AS cnt
        ↓
④ [计算列]           ← yoy_pct = (v_2026 - v_2025) / v_2025
                       price_contrib = ..., qty_contrib = ...
        ↓
⑤ [过滤]             ← 只保留 v_2025 > 100万 美元（去掉噪点小户）
        ↓
⑥ [排序 + 行数限制]  ← 按 yoy_pct 升序，前 50 行
        ↓
                  [输出：明细表 / 柱图 / 折线图]
```

这一串节点，**自动生成的 SQL 等价于**一段包含 `WITH ... AS`、`SUM / COUNT / CASE WHEN / ROUND / ORDER BY / LIMIT` 的复杂查询。**但你不用写代码。**

#### 这一刻，拖出来的到底是个啥？

> **拖出来的不是一张漂亮的图，是一份能跑、能改、能复用的 SQL 脚本。**
> 这就是"拖拽式 SQL"和"画图表工具"的本质区别——后者画的是结果，前者拖的是计算过程。

---

### 步骤 4：验证（工程化思维 · 可验证）

> **不要先激动。** 跑出来一堆数，先别急着解读，先验。

#### 四个验证动作

| 验证 | 怎么做 | 标准 |
|---|---|---|
| **行数核对** | 跟总署下发的贸易统计月报对总数 | 工具数 = 月报数 |
| **空值检查** | 查 HS 编码为空的报关单占比 | < 0.5% 才放心 |
| **极值检查** | 单笔 > 1 亿美元 / < 100 美元的列出来 | 确认不是录错 |
| **抽样回溯** | 随机抽 100 条回 H2010 报关单回执系统比对 | 字段、金额、HS 三件套一致 |

#### 在工具里怎么挂验证节点？

```
[原 SQL 链路]  ── 旁路挂载  ──  [验证节点组]
                                    ↓
                  ┌── [行数核对]
                  ├── [空值检查]
                  ├── [极值检查]
                  └── [抽样回溯]
```

#### 零基础最常犯的错

**❌ 错**："SQL 跑出来了，同比增长 -3.6%，报告。"
**✅ 对**："先验行数对了、空值可控、极值没离谱、抽样能对上——**才能**用 -3.6% 这个数。"

> "可验证"是工程化思维四个特征里最容易被新手忽略、但最值钱的那一格。
> "模型说有疑点，业务说没有，通常不是业务错了。"

---

### 步骤 5：分析（工程化 → 结构化）

> **验证通过，才进入分析。** 否则就是沙上建塔。

#### 在已验证的 SQL 上"加挂"分析节点

```
[已验证的 6 节点链路]
        ↓
   [分组汇总]    ← 按 HS 大类 × 国别 × 企业 三维度分别出表
        ↓
   [TOP N]       ← 每维度取下滑 TOP 20
        ↓
   [同比/环比]   ← 与上年同期对比
        ↓
   [占比/贡献度] ← 算每个 HS 的下滑占总下滑的份额
        ↓
   [图表]        ← 柱图看量、折线看趋势、桑基图看结构
        ↓
   [输出：表 + 图 + 三句话]
```

#### 产出三件套

每张表、每张图背后都要配**三句话**：

| 拆法 | 示例 |
|---|---|
| **空间拆** | "下滑 60% 集中在机电产品，前 3 个 HS 大类贡献了 8 成。" |
| **因果拆** | "量贡献 -2.1pp、价贡献 -1.5pp、结构贡献 +0.4pp——**量价齐跌是主因，结构升级是亮点**。" |
| **主体拆** | "中小企业下滑 -15%，头部企业 +6%，**集中度在上升**。" |

> 这三句话本身又是一次"结构化拆解"——SQL 跑得动是工程化，能讲清楚为什么下滑则是结构化思维的事。

---

### 步骤 6：报告（结构化思维 · 回译闭环）

> 报告不是把表/图粘贴进 PPT，**是用"汇报三步法"重新讲一遍业务问题**。

#### 汇报三步法

**第一步：拆解（结构化思维）**

> "增长乏力，拆开看，主要来自三个维度：
> - 按 HS 大类分，机电产品占出口 60%，今年前八月同比 **-4.2%**，是主力拖累；
> - 按国别分，对东盟 **+12%**，对欧美 **-8%**，**结构在悄悄切换**；
> - 按企业分，中小企业下滑 **-15%**，头部企业反而 **+6%**，**集中度在上升**。"

**第二步：模型（问题模型 + 数学模型）**

> "用 **贸易额 = 量 × 价 × 结构** 一拆：
> 量贡献 **-2.1 个百分点**、价贡献 **-1.5 个百分点**、结构贡献 **+0.4 个百分点**。
> 翻译成业务话——**量价齐跌是主因，结构升级是亮点**。"

**第三步：方案（工程化思维）**

> "建议下一步分三条线核实：
> ① 查机电产品前十大 HS 编码的量价明细，看是订单转移还是价格战；
> ② 拉头部企业新增客户清单，看集中度上升是产业升级还是订单聚集；
> ③ 抽样 5 家中小出口企业，了解是资金压力还是汇率/关税问题。"

#### 报告里**不要出现这些词**

| 不要说 | 应该替换为 |
|---|---|
| "我用了结构化思维" | "我们把问题拆成三块来看" |
| "我用 SQL 跑了一下" | "我们拉了一下数据" |
| "yoy_pct 是 -3.6%" | "今年前八月同比下滑 3.6%" |
| "JOIN 了 6 张表" | "把企业、HS、国别几方面都纳入了分析" |

> **业务点头了，6 步才算闭环。** 反过来，只会念节点、念 SQL 输出，翻译链就是断的——拖出来的不是答案，是半成品。

## 模块 4：快案例迁移 —— "昨天发生了什么？"

> 学员跟着走了一遍慢案例后，用一个更日常的问题检验能不能迁移。
> **建议做成学员练习，而非讲师演示。**

### 业务原话

> "昨天通关数据好像有点异常，看看发生了什么。"

### 学员任务：快速走六步

| 步骤 | 学员要做的事 | 提示 |
|---|---|---|
| ① 拆解 | "异常"跟谁比？哪个维度异常？量还是价？→ 在白纸上拼出公式 | 拆到能落到字段为止 |
| ② 找数 | 昨天的报关单在哪张表？字段口径是什么？→ 画出表关系 | 先只拖数据源节点 |
| ③ 建模 | 拖出节点链：数据源→过滤(昨天)→聚合→计算(偏差)→排序 | 对照 SQL 检查每个节点 |
| ④ 验证 | 行数对不对？空值多少？有没有极端值？ | 四个验证动作都挂上 |
| ⑤ 分析 | 哪个品类/企业/国别偏差最大？→ 写三句话 | 空间/因果/主体各一句 |
| ⑥ 报告 | 用汇报三步法讲出来 | 报告里不许出现技术词 |

### 讲师角色

- 不演示，只纠偏。
- 重点关注：学员是不是跳步了？是不是直接进工具了？
- 六步法的价值不在于"看懂了"，在于"自己做了一遍"。

## 模块 5：避坑清单 + 回译检验

### 五大常见坑

| # | 坑 | 怎么避 |
|---|---|---|
| 1 | 跳过拆解，**直接进工具拖节点** | 强迫自己用 5 分钟白纸写公式，写不出来就别碰工具 |
| 2 | 跳过找数，**口径都没对齐就开始聚合** | 在工具里先**只拖"数据源"节点**，确认字段名、含义、单位 |
| 3 | 跳过验证，**SQL 跑出来就当结论** | 把"行数核对/空值检查/极值检查/抽样回溯"四节点**强制挂上** |
| 4 | 把"分析"当"出图"，**图很漂亮，结论说不清** | 每张图强制配 3 句话（空间/因果/主体） |
| 5 | 报告里**堆 SQL 词、念节点名** | 自查清单：报告里**不许出现** `SELECT / WHERE / JOIN / GROUP BY` |

### 回译检验三问

1. **能不能用一句业务话讲清六步分别是做什么的？**
   （"拆问题 → 找数据 → 拖节点 → 验数 → 分析 → 讲明白"）
2. **能不能把任何一句业务话拆成一个公式？**
   （"今年出口乏力" / "客户流失严重" / "报销太慢"——套步骤 1）
3. **能不能在白板上画出一份"汇报一页纸"？**
   （套步骤 6 的三步法：拆解 → 模型 → 方案）

三个都能，**你就不是零基础了**。

## 模块 6：收尾 —— 四句话带走

1. **拖拽式 SQL 不是"画图工具"，是"不写代码的 SQL 编辑器"**——你拖的是计算过程。

2. **两种思维是骨架，六步是关节，拖拽是肌肉**——三者缺一，模型就瘫。

3. **能拖不代表会分析**——会拖是手艺，会拆问题是判断；手艺决定快不快，判断决定会不会掉坑。

4. **六步闭环的标志是"回译"**——业务能听懂、能点头、能拍板，六步才算完。

## 附录 A：业务 → 模型 → 业务的"方言对照表"

业务话天然含糊，模型话必须精确。日常功课就是这张对照表的翻译：

| 业务怎么说 | 模型 / SQL 需要什么 |
|---|---|
| "增长乏力" | 基准（跟谁比）、幅度（低多少）、维度（按国家/HS/企业/贸易方式） |
| "今年明显不如去年" | 同比窗口、统计口径（人民币/美元）、是否含跨境电商 |
| "感觉某地流失严重" | "流失"的定义：转关？还是转港？转去哪个关区？ |
| "重点关注这几家" | 排序规则、TOP N、阈值（按绝对额？还是按同比？） |
| "这事儿挺严重" | 严重程度的量化标尺（同比下滑 ≥ 30%？绝对额 ≥ 1 亿美元？） |
| "查一下" | 时间窗、范围、筛除条件、输出列、保密级别 |

**翻译不动的地方，就是要跟业务当面聊的地方——这本身就是需求澄清。**

## 附录 B：五种汇报模板速记

| 模板 | 业务原话 | 对应思维 | 对应步骤 |
|---|---|---|---|
| 拆解结构 | "问题主要由三个因素组成" | 结构化思维 | 步骤 1 |
| 公式结构 | "可以用一个简单模型理解" | 问题模型 | 步骤 1 → 2 |
| 因果结构 | "主要原因有三个" | 归因分析 | 步骤 5 |
| 流程结构 | "整个方案分为四步" | 工程化路径 | 步骤 3 → 5 |
| 方案结构 | "我们有三个解决方向" | 工程化思维 | 步骤 6 |

汇报时**不要说"我用了结构化思维"**——把方法论翻成"三个因素/一个公式/三步方案"这种业务听得懂的句子，这本身就是结构化思维的最高段位。
