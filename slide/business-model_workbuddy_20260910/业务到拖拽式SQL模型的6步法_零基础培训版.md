# 业务 → 拖拽式 SQL 模型：零基础的 6 步法

> **培训对象**：数据分析零基础学员
> **核心讲法**：用 **结构化思维** + **工程化思维** 两条主线，**一步一步** 把一句业务话，**拖成一个能跑出数来的可视化 SQL 模型**。
> **贯穿示例**：海关业务 —— **"今年出口贸易增长乏力，到底乏力在哪？"**
> **配套资料**：《结构化思维与工程化思维》总结摘要；slide/20260910.md 讲稿；slide/20260910.html 演示页；slide/业务到数据分析模型的转化_通俗解释.md（思维科普版）。

## 工具箱：本文用到的 3 个核心概念（先看这一页）

> **后文出现的所有概念都汇总在这里**。记不住就翻回这里查。

### 一、结构化思维

| 维度 | 说明 |
|---|---|
| **一句话** | 把含糊的问题**拆清楚、说清楚** |
| **干什么用** | 解决"如何**看清**问题" |
| **4 个动作** | ① 分解（拆成小块） ② 分类（互不重叠） ③ 构建逻辑关系（因果/层级） ④ 可表达（能画成图/写成公式） |
| **在本篇里出现** | 步骤 1（拆解）、步骤 2（找数）、步骤 6（报告） |

### 二、工程化思维

| 维度 | 说明 |
|---|---|
| **一句话** | 把问题变成**能落地、能验证、能迭代**的系统 |
| **干什么用** | 解决"如何**改变**现实" |
| **4 个特征** | ① 问题可定义（输入/输出/约束） ② 系统设计（模块化） ③ 可验证（指标/测试） ④ 迭代（闭环改进） |
| **在本篇里出现** | 步骤 2（找数）→ 步骤 3（建模）→ 步骤 4（验证）→ 步骤 5（分析） |

### 三、模型（3 种）

| 模型 | 一句话人话 | 在本篇对应什么 |
|---|---|---|
| **问题模型** | 一个用来理解复杂问题的简单公式 | 步骤 1 出来的"贸易额 = Σ HS × 单价 × 数量" |
| **信息模型** | 组织数据的结构（表/字段/口径） | 步骤 2 出来的"报关单 + 4 张维表" |
| **数学模型** | 用于预测或计算的数学公式 | 步骤 3 拖出来的"6 节点可视化 SQL 链" |

> **速记口诀**：问题模型 = 公式；信息模型 = 表格；数学模型 = SQL/算法。

### 四、两种思维的关系（一句话）

> 工程化思维**包含**结构化思维。一般路径：
> **结构化思维**（看清问题）→ 建出问题模型 → **工程化思维**（设计系统）→ 产出信息模型和数学模型 → 解决现实问题。

## 〇、写在前面：两句话定调

**第一句：新手不是不会分析，是不会写 SQL 代码。**
所以我们用"**拖拽式 SQL**"——把代码变成"乐高积木"：每个节点就是一段 SQL，连起来就是一段能跑的查询。**你拖的不是花哨的可视化，是 SQL 代码本身**。

**第二句：拖拽只是省了"写字"，省不了"想清楚"。**
拖什么节点、怎么连、按什么顺序，全靠**两种思维**撑起来：

- **结构化思维** —— 解决"如何看清问题"
- **工程化思维** —— 解决"如何改变现实"

下面 6 步，**1、2、6 偏结构化**（拆、找、讲），**3、4、5 偏工程化**（建、验、用）。

## 一、6 步全图（先看一眼，细节后头展开）

| # | 阶段 | 主要思维 | 关键动作 | 产出物 |
|---|---|---|---|---|
| 1 | **拆解** | 结构化 | 把含糊的业务话拆成几个不重叠的部分，再拼成公式 | 一张**问题公式**（白纸/Word） |
| 2 | **找数** | 结构化 → 工程化 | 公式里的变量，对应到具体的数据源和字段 | 一张**信息模型图**（主表+维表） |
| 3 | **建模（拖拽式 SQL）** | 工程化 | 在工具里**拖节点、连节点**，拼出可视化 SQL | 一张**节点连线图**（可视化 SQL） |
| 4 | **验证** | 工程化 | 跑一遍对账：行数、空值、极值、回抽样 | 一份**验证清单**（对得上/对不上） |
| 5 | **分析** | 工程化 → 结构化 | 在已验证的 SQL 上加分组、TOP N、同比节点 | 一张**表/图 + 三句话** |
| 6 | **报告** | 结构化 | 用汇报三步法讲：拆解 → 模型 → 方案 | **一页纸结论** |

**贯穿海关例（一句业务话）**：

> "今年出口贸易增长乏力，怎么看？"

下面就用这一句话，**从头拖到尾**。

## 二、步骤 1：拆解（结构化思维）

> **这一阶段不进工具**。拿白纸或 Word 写就行。

### 1.1 业务原话

> "今年出口贸易增长乏力，得查查怎么回事。"

——这跟"这个月费用怎么这么高"是同款含糊：**带情绪、有方向、没动作**。

### 1.2 拆解动作：三问

| 问什么 | 海答案例 | 为什么重要 |
|---|---|---|
| **跟谁比？** | 跟去年同期比 / 跟全国均值比 / 跟兄弟关比 | 没有基准，"乏力"二字就站不住 |
| **乏力在哪？** | 国家、HS 大类、企业主体、贸易方式 | 不拆维度，永远在原地打转 |
| **为什么乏力？** | 量（单数/货值/数量）？价（单价）？结构变了？ | 拆因才能拆方案 |

### 1.3 拼成公式（问题模型）

```
出口贸易额 = Σ 各 HS 编码 × 单价 × 数量
同比增长率 = (本期贸易额 − 同期贸易额) ÷ 同期贸易额
乏力归因  = 量贡献 + 价贡献 + 结构贡献
```

> 此刻**一个数字都没有**。但问题已经被"拆开、说清"。这就是《总结摘要》说的"问题模型"——一个用来理解复杂问题的简单框架或公式。

### 1.4 零基础自检：拆到什么时候停？

**答：拆到"能落到一张表的一个字段"为止。** 比如"按 HS 大类"还不够，HS 大类存在哪张表的哪个字段？想到了，就停笔，进步骤 2。

### 1.5 这一步在两种思维里是谁？

**结构化思维** —— 解决"如何看清问题"。特征：**分解、分类、构建逻辑关系**。

---

## 三、步骤 2：找数（结构化 → 工程化）

> 这一步要进工具了，但**只是摸数据，不动计算**。

### 3.1 把公式里的变量，翻译成"数据在哪儿"

| 公式里的变量 | 数据落在哪（信息模型） | 零基础要问的"口径坑" |
|---|---|---|
| 贸易额 | 报关单 × 总价（统计美元价） | 用 `美元` 还是 `人民币`？含运保费吗？ |
| 数量 | 报关单 × 数量 + 法定单位 | 散货 / 整柜 / 第二计量单位怎么折？ |
| HS 编码 | 报关单 × 商品编码 | 拆到 4 位 / 6 位 / 8 位？ |
| 出口主体 | 报关单 × 经营单位代码 | 含不含跨境电商、海外仓？ |
| 同期数据 | 历史归档表 | 行政区划调整过没？编码版本换过没？ |
| 异常筛除 | 报关单 × 状态 + 担保标志 | 含不含"已删单"？"异常补税"？ |

### 3.2 在工具里做什么？

在拖拽式工具里**拖一个"数据源"节点**，把它配置成：

```
[数据源节点：报关单]
   ├── 来自：报关单主表
   ├── 关联：商品归类表（按 HS 编码）
   ├── 关联：企业备案表（按经营单位代码）
   ├── 关联：国别代码表（按目的国）
   └── 关联：历史归档表（按月份）
```

> 这就是《总结摘要》说的"信息模型"——"组织数据的结构（如：数据库表设计）"。

### 3.3 零基础最常犯的错：跳过这一步直接建模

**❌ 错**：上来就拖【过滤】【聚合】节点，**数据从哪来都没搞清楚**。
**✅ 对**：先把 6 张表的关系画清楚，**再用工程化的态度进工具**。

### 3.4 这一步在两种思维里是谁？

**结构化 → 工程化**——看清变量之后，**用工程化思维**把它们组织成可定义、可模块化、可约束的表结构。
特征：**问题可定义（输入/输出/约束）、系统设计（模块化）**。

## 四、步骤 3：建模 —— 拖拽式 SQL 核心（工程化思维）

> **这是培训的核心**。新手不会写 SQL，那就**把 SQL 拆成节点，一个一个拖**。

### 4.1 一句话理解"拖拽式 SQL"

**普通 SQL 代码**：

```sql
SELECT hs4, SUM(total_price_usd) AS sum_c
FROM   customs_declaration
WHERE  ie_flag = 'E'
  AND  decl_date BETWEEN '2026-01-01' AND '2026-08-31'
GROUP  BY hs4
ORDER  BY sum_c DESC
LIMIT  20;
```

**拖拽式 SQL（同一段查询的"节点形态"）**：

```
[数据源：报关单]  →  [过滤：出口 + 2026-01-01~2026-08-31]
                              ↓
                   [聚合：按 hs4 分组, SUM(总价)]
                              ↓
                   [排序：按 sum_c 降序]
                              ↓
                     [行数限制：前 20 行]
```

**每个节点 = 一段 SQL 代码，你只是没看见它**。工具会自动拼成上面那段 SELECT-WHERE-GROUP BY。

### 4.2 海关版完整 6 节点链路

> 一条线从数据源拖到输出端，覆盖整个"出口增长乏力"问题。

```
① [数据源：报关单]   ← 步骤 2 配好的主表 + 4 张维表
        ↓
② [过滤]             ← ie_flag = '出口' AND 时间窗 IN (2025年, 2026年)
        ↓
③ [聚合]             ← 按 hs4, dest_country, decl_company 分组
                       SUM(总价美元) AS v, COUNT(*) AS cnt
        ↓
④ [计算列]           ← yoy_pct = (v_2026 - v_2025) / v_2025
                       price_contrib = ..., qty_contrib = ...
        ↓
⑤ [过滤]             ← 只保留 v_2025 > 100万 美元（去掉噪点小户）
        ↓
⑥ [排序 + 行数限制]  ← 按 yoy_pct 升序，前 50 行
        ↓
                  [输出：明细表 / 柱图 / 折线图]
```

> 这一串节点，**自动生成的 SQL 等价于**一段包含 `WITH … AS` 公共表表达式、`SUM / COUNT / CASE WHEN / ROUND / ORDER BY / LIMIT` 的复杂查询。**但你不用写代码**。

### 4.3 零基础小贴士：每个节点在"两种思维"里是谁？

| 节点 | 主要思维 | 一句话解释 |
|---|---|---|
| ① 数据源 | 工程化 | 把所有可能用到的表，**先都摆上桌** |
| ② 过滤 | 结构化 | 把不符合口径的**一刀切掉**——口径错了后面全错 |
| ③ 聚合 | 结构化 | 把明细**压缩成口径一致的合计** |
| ④ 计算列 | 工程化 | 把业务关心的派生指标**算出来**（同比、贡献度） |
| ⑤ 过滤 | 工程化 | 把"噪点"剔掉，让结论站得住 |
| ⑥ 排序 + 行数限制 | 结构化 | 把答案**按业务可读的方式排出来** |

### 4.4 这一刻，业务问题已经被"翻译"成了一段可视化 SQL

《总结摘要》说的"数学模型"——用于预测或计算的数学公式——**此刻具象成了这串节点**。

### 4.5 这一刻，拖出来的到底是个啥？

> **拖出来的不是一张漂亮的图，是一份能跑、能改、能复用的 SQL 脚本。**
> 这就是"拖拽式 SQL"和"画图表工具"的本质区别——后者画的是结果，前者拖的是计算过程。

## 五、步骤 4：验证（工程化思维 · 可验证）

> **不要先激动。** 跑出来一堆数，先别急着解读，先验。

### 5.1 在工具里加 4 类"验证节点"

```
[原 SQL 链路]  ── 旁路挂载  ──  [验证节点组]
                                    ↓
                  ┌── [行数核对]     本期 vs 同期 vs 业务部门手工合计
                  ├── [空值检查]     HS 编码 / 经营单位 / 金额是否齐全
                  ├── [极值检查]     单笔最大、最小、是否为离群点
                  └── [抽样回溯]     随机抽 100 条回原系统比对
```

### 5.2 海关例：四个验证的"动作"是什么？

| 验证节点 | 海关版动作 | 验什么 |
|---|---|---|
| 行数核对 | 跟总署下发的贸易统计月报对总数 | 工具数 = 月报数？ |
| 空值检查 | 查 HS 编码为空的报关单占比 | < 0.5% 才放心 |
| 极值检查 | 单笔 > 1 亿美元 / < 100 美元的报关单列出来 | 看看是不是录错 |
| 抽样回溯 | 抽 100 条回 H2010 报关单回执系统比对 | 字段、金额、HS 三件套一致 |

### 5.3 零基础最常犯的错：跳过这一步直接给结论

**❌ 错**："SQL 跑出来了，同比增长 -3.6%，报告。"
**✅ 对**："先验行数对了、空值可控、极值没离谱、抽样能对上——**才能**用 -3.6% 这个数。"

> 《总结摘要》原话："**可验证**"是工程化思维的核心特征之一。
> 讲稿（slide/20260910.md）也强调过："模型说有疑点，业务说没有，通常不是业务错了。"——验证就是预防这种尴尬。

### 5.4 这一步在两种思维里是谁？

**纯工程化**——**可验证**是工程化思维四个特征里最容易被新手忽略、但最值钱的那一格。

## 六、步骤 5：分析（工程化 → 结构化）

> **验证通过，才进入分析**。否则就是沙上建塔。

### 5.5 在已验证的 SQL 上，"加挂"分析节点

```
[已验证的 6 节点链路]
        ↓
   [分组汇总节点]    ←  按 HS 大类 × 国别 × 企业 三维度分别出表
        ↓
   [TOP N 节点]      ←  每维度取下滑 TOP 20
        ↓
   [同比 / 环比节点]  ←  与上年同期 / 上月对比
        ↓
   [占比 / 贡献度节点] ←  算每个 HS 的下滑占总下滑的份额
        ↓
   [图表节点]         ←  柱图看量、折线看趋势、桑基图看结构
        ↓
   [输出：表 + 图 + 三句话]
```

### 6.1 海关版"三句话"怎么来？

每张表、每张图背后都要配三句话，**这三句话本身又是一次"结构化拆解"**：

| 拆 | 例 |
|---|---|
| **空间拆** | "下滑 60% 集中在机电产品，前 3 个 HS 大类就贡献了 8 成。" |
| **因果拆** | "量贡献 -2.1pp、价贡献 -1.5pp、结构贡献 +0.4pp——**量价齐跌是主因，结构升级是亮点**。" |
| **主体拆** | "中小企业下滑 -15%，头部企业 +6%，**集中度在上升**。" |

### 6.2 零基础自检：分析做完要交付什么？

**一个固定的三件套**：
1. **一张表**（明细或汇总）
2. **一张图**（柱/折线/桑基，挑合适的）
3. **三句话**（空间 / 因果 / 主体 拆一下）

> 这就是《总结摘要》"四层抽象"里**事实层 + 功能层**的产物——你看到的（表/图）和你想表达的（三句话）。

### 6.3 这一步在两种思维里是谁？

**工程化 → 结构化**——SQL 跑得动是工程化，能**讲清楚**为什么下滑则是结构化思维的事。
特征对应：**迭代**（工程化） + **构建逻辑关系**（结构化）。

## 七、步骤 6：报告（结构化思维 · 沟通）

> 报告不是把表/图粘贴进 PPT，**是用"汇报三步法"重新讲一遍业务问题**。

### 7.1 《总结摘要》给的"经典汇报三步法"原话

> "我们先把问题拆开来看（拆解）→ 从结构上可以用一个简单模型理解（公式）→ 因此解决路径主要分为三步（方案/工程化）。"

### 7.2 海关版完整一页纸（对着领导/业务部门这样讲）

#### 第一步：拆解（结构化思维）

> "增长乏力，拆开看，主要来自 **三个维度**：
> - 按 HS 大类分，机电产品占出口 60%，今年前八月同比 **-4.2%**，是主力拖累；
> - 按国别分，对东盟 **+12%**，对欧美 **-8%**，**结构在悄悄切换**；
> - 按企业分，中小企业（出口额 < 5000 万美元）下滑 **-15%**，头部企业反而 **+6%**，**集中度在上升**。"

> 对应《总结摘要》的"**拆解结构**"模板："这个问题主要由三个因素/部分组成。"

#### 第二步：模型（问题模型 + 数学模型）

> "用 **贸易额 = 量 × 价 × 结构** 一拆：
> 量贡献 **-2.1 个百分点**、价贡献 **-1.5 个百分点**、结构贡献 **+0.4 个百分点**。
> 翻译成业务话——**量价齐跌是主因，结构升级是亮点**。"

> 对应"**公式/模型结构**"模板："这个业务可以用一个简单公式/框架来理解。"

#### 第三步：方案（工程化思维）

> "建议下一步分 **三条线**核实：
> ① 查机电产品前十大 HS 编码的量价明细，看是订单转移还是价格战；
> ② 拉头部企业新增客户清单，看集中度上升是产业升级还是订单聚集；
> ③ 抽样 5 家中小出口企业，了解是资金压力还是汇率/关税问题。"

> 对应"**方案结构**"模板："针对这个问题，我们有三个解决方向。"

### 7.3 零基础小贴士：报告里**不要出现这些词**

| 不要说 | 为什么 | 应该怎么替换 |
|---|---|---|
| "我用了结构化思维" | 方法论名词，业务听不懂 | "我们把问题拆成三块来看" |
| "我用 SQL 跑了一下" | 技术词 | "我们拉了一下数据" |
| "yoy_pct 是 -3.6%" | 直接念 SQL 输出 | "今年前八月同比下滑 3.6%" |
| "JOIN 了 6 张表" | 暴露工程细节 | "把企业、HS、国别几方面都纳入了分析" |

> **业务点头了，6 步才算闭环。** 反过来，只会念节点、念 SQL 输出，翻译链就是断的——拖出来的不是答案，是半成品。

### 7.4 这一步在两种思维里是谁？

**纯结构化**——把工程化的产物**翻译回业务话**。这一步比"建模"更难练、也更容易被忽略。

## 八、6 阶段 × 2 思维 × 拖拽动作 一图速记

```
业务话："出口增长乏力"               业务话："量价齐跌，结构升级"
     │                                       ▲
     ▼  ①拆解(结构化)                        │
[问题模型=贸易额×量×价×结构]                │
     │                                       │
     ▼  ②找数(结构化→工程化)                 │
[信息模型=报关单+4张维表]                    │
     │                                       │
     ▼  ③建模(工程化)                        │
[数据源]→[过滤]→[聚合]→[计算列]→[过滤]→[排序]  │   回译：
   ↑       ↑       ↑       ↑       ↑       ↑   │   ⑥报告(结构化)
   │       │       │       │       │       │   │   汇报三步法
   └───── ④验证(工程化)──────┘               │
              └──── ⑤分析(工程化→结构化)──┘───┘
```

**整条线读下来**：

- **1→2 走结构化**（看清问题）
- **3→4→5 走工程化**（建系统 + 验 + 用）
- **6 回到结构化**（讲明白）

**两种思维交替出现，缺一不可。**

## 九、零基础 5 大常见坑（避坑清单）

| # | 坑 | 怎么避 |
|---|---|---|
| 1 | 跳过拆解，**直接进工具拖节点** | 强迫自己用 5 分钟白纸写公式，写不出来就别进工具 |
| 2 | 跳过找数，**口径都没对齐就开始聚合** | 在工具里先**只拖"数据源"节点**，确认字段名、字段含义、单位 |
| 3 | 跳过验证，**SQL 跑出来就当结论** | 把"行数核对 / 空值检查 / 极值检查 / 抽样回溯"四节点**强制挂上** |
| 4 | 把"分析"当"出图"，**图很漂亮，结论说不清** | 每张图强制配 3 句话（空间 / 因果 / 主体） |
| 5 | 报告里**堆 SQL 词、念节点名** | 自查清单：报告里**不许出现** `SELECT / WHERE / JOIN / GROUP BY` 这类词 |

## 十、怎么知道你真的"会了"？——回译检验

《总结摘要》说过一句话："转化的验收标准是回译——业务能点头，才算数。"

**自检三问**：

1. **能不能用一句业务话讲清 6 步分别是做什么的？**（"拆问题→找数据→拖节点→验数→分析→讲明白"）
2. **能不能把任何一句业务话（"今年出口乏力"/"客户流失严重"/"报销太慢"）拆成一个公式？**（套步骤 1）
3. **能不能在白板上画出一份"汇报一页纸"？**（套步骤 6 的三步法）

三个都能，**你就不是零基础了**。

## 十一、四层抽象 · 自检表（给学员的"思考深度参考"）

《总结摘要》给的"四层抽象"——**任何复杂的思维方法/工具/系统，都可以从这四层讲清楚**。
套到"业务→拖拽式 SQL 6 步法"上：

| 层级 | 6 步法里的样子 | 培训里怎么教 |
|---|---|---|
| 事实层（看到什么） | 工具里那串节点连线图、跑出来的表/图 | 让学员**先照着拖一遍**——有形可依 |
| 功能层（在做什么） | 把一句业务话翻译成可计算、可复核的数字 | 让学员**对比"翻译前 vs 翻译后"**，体会差异 |
| 逻辑层（怎么运作） | 6 步法的两思维（结构化 + 工程化） | 让学员**说出每一步在用哪种思维**——从形到神 |
| 原理层（为什么有效） | 短期记忆分块（结构化原理）+ 输入/输出/约束（工程化原理） | 只在被追问时讲，避免零基础被劝退 |

> 培训节奏建议：**事实层 → 功能层 → 逻辑层** 必讲，**原理层** 留到收尾或答疑。

---

## 十二、记住四句话

1. **拖拽式 SQL 不是"画图工具"，是"不写代码的 SQL 编辑器"**——你拖的是计算过程。
2. **两种思维是骨架，6 步是关节，拖拽是肌肉**——三者缺一，模型就瘫。
3. **能拖不代表会分析**——会拖是手艺，会拆问题是判断；手艺决定快不快，判断决定会不会掉坑。
4. **6 步闭环的标志是"回译"**——业务能听懂、能点头、能拍板，6 步才算完。
